# 技術方針・機能要件

## 1. 実装難易度の評価

**低い。** すべて枯れたライブラリで解ける問題であり、AI 活用前提なら MVP は数週間規模。

本プロジェクトのボトルネックは開発ではなく販路である（[05-feasibility.md](./05-feasibility.md) 参照）。したがって技術選定は**最小構成で始め、必要になってから足す**方針を徹底する。

## 2. データフロー

1. 利用者が CSV / `.xlsx` をドラッグ＆ドロップ
2. Web Worker 内でパース
3. 列（ヘッダー）のマッピングを指定（日付軸 / 数値軸 / カテゴリ軸 / フィルタ軸）
4. 整形済みデータを IndexedDB へ保存
5. インメモリ集計 → グラフ描画

## 3. 技術スタック

| 領域 | 採用 | 備考 |
| --- | --- | --- |
| フロントエンド | 静的サイト（SSG / Static Export） | サーバーサイド処理を持たない |
| CSV パース | PapaParse | ストリーミング対応。**文字コード判定は行わないため自前で実装する**（[06-design.md](./06-design.md) §6） |
| Excel パース | SheetJS または exceljs | 日付シリアル値の扱いに注意 |
| ローカル DB | IndexedDB（Dexie.js） | |
| 集計 | **素の JS** | 下記参照 |
| 可視化 | **Apache ECharts** | ヒートマップと dataZoom が標準搭載。選定理由は [06-design.md](./06-design.md) §8 |
| オフライン | Service Worker (PWA) | |

### 3.1 DuckDB-Wasm は初期採用しない

当初案にあったが、**現時点では過剰である**。

- 想定する明細 CSV は数万行規模であり、素の JS 集計で十分処理できる。
- Wasm バイナリが数十 MB 規模になり、オフライン PWA のキャッシュ戦略と相性が悪い。
- 依存が増えるほど「通信先一覧・送信内容保証書」の作成コストと監査面積が増える。

性能が実測で不足した時点で導入を検討する。

### 3.2 外部 CDN の使用禁止

CSP で通信先を 1 ドメインに固定するため、フォント・ライブラリを含め**すべて自ホストする**。これは制約ではなく仕様である。

## 4. 機能要件

### A. データ入力・解析

- CSV / `.xlsx` のドラッグ＆ドロップ読み込み
- Shift-JIS / UTF-8 の文字コード自動判別（TextDecoder による自前判定）
- ヘッダー列の自動抽出とプレビュー表示

### B. 列マッピング

- 日付軸 / 数値軸 / カテゴリ軸 / フィルタ軸の動的割り当て
- フォーマット別の**マッピングプリセット保存**（銀行・カード会社・会計ソフトごと）

### C. 可視化・ダッシュボード

- グラフ種別の切り替え（折れ線 / 棒 / 円 / ヒートマップ）
- 集計単位の切り替え（日 / 週 / 月 / 年 × 合計 / 平均 / 件数）
- 日付範囲・カテゴリによる絞り込み

### D. ローカルデータ管理

- IndexedDB への保存
- 暗号化 JSON でのエクスポート / インポート
- 全データ削除

### E. 有料機能

- 顧問先ごとのワークスペース切り替え
- 対前年比・期間比較
- PDF レポート出力（ヘッダー / フッター整形、ロゴカスタマイズ）

## 5. 想定される実装上の泥仕事

難所ではないが工数を食う箇所。見積もりから漏らさないこと。

- 文字コード判定（Shift-JIS の誤判定）
- Excel の日付シリアル値・書式付きセルの解釈
- 銀行・カード会社ごとの CSV 方言（ヘッダー行の位置、金額の符号、全角数字、桁区切り）
- 金額列の型推定（`1,234` `▲1,234` `(1,234)` 等）

## 6. 運用コスト

- 静的ホスティングのみ。バックエンドはライセンス検証 API 1 本。
- 利用者データを保持しないため、**バックアップ・暗号化・漏洩対応の運用負荷がほぼゼロ**。
- オンコール不要。

個人開発者にとって理想的な運用形態である。
