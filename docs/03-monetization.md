# 課金モデル・料金設計

## 1. 結論

**無料 = 非商用・機能制限 / 有料 = 商用ライセンス + シート数申告制の年額サブスクリプション**

技術的な強制はライセンスキーの検証のみに留め、利用人数は契約ベースで信用する。

## 2. 却下案：PC 台数によるフリーミアム（例「5 台まで無料」）

### 2.1 却下の主因：市場規模

**士業事務所の大半は数人規模である。5 台無料とすると、想定顧客の大半が永久に課金対象にならない。**

カウント精度が完璧であってもこの一点で成立しない。したがってこれは技術問題ではなく市場設計の問題である。

### 2.2 副次的な理由：無料枠の台数計測が困難

有料側の台数カウントは**可能**である（ライセンスキー + サーバー側アクティベーション数管理。一般的なデスクトップアプリと同じ）。問題は無料側にある。

| 手段 | 問題 |
| --- | --- |
| localStorage の UUID | シークレットモード・キャッシュ削除・ブラウザ変更で別端末扱いになる |
| フィンガープリンティング | **プライバシー訴求と真っ向から矛盾する**。発覚時のブランド毀損が致命的 |
| アカウント必須化 | toB のコンバージョンを大きく落とす。パスワードリセット等のサポート負荷が発生 |

### 2.3 副次的な理由：サポート負荷

台数管理は個人開発者にとって問い合わせの温床となる。

- PC の買い替えに伴う枠の付け替え
- 退職者の枠解放
- ブラウザ変更で枠が減った、という申告

これらをすべて開発者本人が捌くことになる。**台数で課金しない最大の実務的理由はここにある。**

## 3. 採用モデル

### 3.1 無料プラン（評価・導線用）

| 項目 | 内容 |
| --- | --- |
| 用途 | 非商用・評価目的のみ（業務利用は不可と明記） |
| ファイル読み込み | 単一ファイル |
| グラフ | 基本種別のみ |
| PDF 出力 | ウォーターマーク入り |
| マッピングプリセット保存 | 不可（またはごく少数） |
| ワークスペース | 単一 |

無料版の役割は**購入判断のための試用導線**であり、実務で常用できる水準には置かない。

### 3.2 有料プラン（事務所単位・年額）

| 項目 | 内容 |
| --- | --- |
| 商用利用ライセンス | 付与 |
| ワークスペース | 顧問先ごとに複数 |
| マッピングプリセット | 無制限 |
| 分析機能 | 対前年比、期間比較 |
| PDF 出力 | ロゴ非表示・事務所名等のカスタマイズ可 |
| 提供資料 | 通信先一覧・送信内容保証書 |
| オフライン版 | 署名ライセンスファイル方式を提供 |

### 3.3 料金階段（シート数申告制・金額は仮置き）

| 区分 | 想定 |
| --- | --- |
| 1〜5 名 | 小規模事務所向け |
| 6〜20 名 | 標準 |
| 21 名〜 | 個別見積 |

金額は市場検証後に確定する。年額サブスクリプションを基本とし、通信を許可できない顧客向けにオフライン版の買い切りを別途用意する。

## 4. 設計上の要点

### 4.1 「業務で使うなら有料」という単一の線引き

士業の業務利用は**定義上すべて商用**である。したがって「台数」ではなく「商用利用か否か」で切ることで、

- 判定が明快（利用者が迷わない）
- 回避されにくい（企業は規約違反のリスクを取らない）
- 実装が最も軽い（ライセンスキー検証だけで済む）

の 3 点が同時に得られる。

### 4.2 技術的強制は最小限に

ライセンスキーの署名検証以外の強制機構は実装しない。法人顧客に対する強制力は**技術ではなく契約**が担保する。個人開発者が運用できる唯一のモデルである。
