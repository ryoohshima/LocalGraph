# 通信方針とセキュリティ設計

本製品の中核であり、営業資料の実体でもある。

## 1. 方針転換：完全通信ゼロ → 通信あり・データ送信なし

### 1.1 当初案（完全通信ゼロ）の問題

`connect-src 'none'` によりネットワーク要求を全遮断する案は、以下を同時に不可能にする。

- ライセンス検証（＝課金の強制力が存在しない）
- 利用状況の把握（＝プロダクト改善が回らない）
- アップデート配信

無料枠の制限をクライアント JS 内に置くしかなくなるが、**本製品を選ぶ層は DevTools で制限を外せる層**であり、実効性がない。

### 1.2 採用方針

> **通信は行う。ただし利用者のデータ（CSV/Excel の中身）は一切送信しない。**

これにより課金・改善・配信の問題がすべて解ける。セキュリティ訴求も弱まらない。守るべきは「データを送らない」ことであり、「通信しない」ことではない。

## 2. 遵守すべき 4 条件

この 4 つが崩れると製品の存在意義が消える。実装上の絶対制約とする。

### 条件 1: 通信先は 1 ドメインのみ

CSP で固定し、それ以外への通信を不可能にする。

```
connect-src 'self' https://license.example.com;
```

外部 CDN・フォント・アナリティクス等の**追加を一切許可しない**。第三者ドメインが 1 つでも増えた時点で監査が通らなくなる。

### 条件 2: 送信内容はライセンスキーと起動イベントのみ

送信する全項目をドキュメントとして公開する。想定する送信データ：

- ライセンスキー
- アプリのバージョン
- 起動日時

ファイル名・列名・セル値・集計結果は**一切含めない**。

### 条件 3: パース処理をワーカー内で完結させる

CSV/Excel のパース・集計を Web Worker 内で行い、ネットワーク送信経路と物理的に分離する。「送らない」を運用ルールではなくコード構造で担保する。

### 条件 4: オフラインライセンス版を用意する

公開鍵による署名検証のみで動作するライセンスファイル方式を併せて提供する。通信を許可できない閉域網の顧客への保険であり、条件 1 の副作用（後述）に対する回避策となる。

## 3. 副作用：情シスの審査カテゴリが変わる

通信が発生した瞬間、企業側の扱いが変わる点は正直に認識しておく。

| | 通信ゼロ | 通信あり（1 ドメイン） |
| --- | --- | --- |
| FW 許可申請 | 不要 | **必要になる場合がある** |
| 委託先管理の対象 | 対象外 | **対象になり得る** |
| プライバシーポリシー | 実質不要 | **必要** |
| 導入までの期間 | 短い | 長くなる |

→ 条件 4 のオフライン版が、この障壁に当たった顧客への回答になる。

## 4. 提供ドキュメント：「通信先一覧・送信内容保証書」

当初「通信ゼロ保証仕様書」と呼んでいたものを、実態に合わせて改名する。**情シスが実際に監査するのはここ**であり、本製品最大の差別化資産となる。

記載内容：

1. 通信先ドメインの全一覧（1 件）
2. 送信データの全項目と、送信タイミング
3. CSP 設定の実物
4. 利用している第三者ライブラリの一覧とライセンス
5. 検証手順（ブラウザの Network タブで再現可能な確認方法）
6. データの保存場所（IndexedDB）と削除方法

## 5. 表現上の注意

「ネットワークレベルで通信を遮断」といった過剰な表現は使用しない。CSP はブラウザが強制する仕組みであり、**配信されるページを信頼する前提**は残る。この点を仕様書に正直に記載することが、かえって情シスからの信頼につながる。

## 6. ローカルデータの取り扱い

- 保存先は IndexedDB のみ。
- バックアップ用の暗号化 JSON エクスポート / インポートを提供する。
- 全データ削除機能を明示的に提供する。
- サーバー側で利用者データを保持しないため、**事業者側に情報漏洩の賠償リスクがほぼ存在しない**。これは個人開発で toB 機密データ領域を扱ううえで決定的な利点である。
